deploy llm dockers on salad (qwen, swift etc). Salad is limited to 1 gpu per container, so, you're maxed by 5090. You have everything prepared for claude / cline (cline is (IMHO) just faster for routine tasks, claude seems to be more capable). I use this for deploying my llama-cpp on salad on demand, switching cards and quantities of cards. Cline runs on default gguf's templates, template for claude is rectified in docker (1 line edit), so, you will need to tell script if you're using llm for claude or not. I started coding it with cline, switched to claude, so, initial export of promt for working with salad's api is left in .clinerules. 

Salad uses it's own api key to secure acces to cloudflare gw, so, you have to run harness via proxy which will add salad's key to llama's requests (if you're a security maniac, you can set llama's api key also, it's coded/tested, but i don't use it, since i work 100% with local llms). Everything was coded with qwen3.8 27b q6k served by vllm on 2 3090.

Docker image is a git cloned llama-server compiled with cuda sdk 12.8 (runs on 3090 & 5090) serving Qwen3.8 (quant + ctx-len per card — target matrix in `docker/README.md`: ≥90K → Q5_K_M on 24 GB / Q6_K on 32 GB; ≥128K → Q6_K on 32 GB, or Q4_K_M on 24 GB). latest dockerfile is  Dockerfile.lmss_generic

## Layout

- `salad_client.py` — stdlib-only Salad OpenAPI client (groups, projects, GPU classes, PATCH via `update_container_group`). API key from `salad_api.txt` (gitignored, never printed).
- `deploy_qwen38_27b.py` — canonical create-or-update deployer for the live group `qwen38-27b-q6k` (the production 27B Claude Code backend) on the baked q6-mtp-vision image (draft + mmproj baked in, only the main model fetched via `hf`). `--org`, `--project`, `--group`, `--gpu rtx5090|rtx3090`, `--model-file`, `--ctx-size`, `--image`, `--use-draft-model`, `--no-start`. Built-in defaults = the live production profile (Q5_K_M @ CTX 90000 on rtx3090, digest-pinned v4 image) — a bare run re-applies exactly that (idempotent against the live group).
- `llama_stats.py` — repo-root entry point for llama-server stats (generation/prompt tps, queue, token totals, spec-decode) scraped from `/metrics`. Run it from the host against a Salad gateway URL (Salad key auto-loaded from `salad_api.txt`) or any local server: `python3 llama_stats.py https://<group>.salad.cloud [--raw] [--interval 2]`. Implementation lives in `docker/llama_stats.py` (must be inside the build context); the in-container wrapper `stats.sh` is installed in the image by `Dockerfile.multistage`.
- `billing.py` — per-org Salad portal credit balances (USD + live EUR column). The public API has no billing operation, so it logs into the portal backend with credentials from `portal_vault.gpg` (GPG AES256, gitignored; passphrase via `$PORTAL_VAULT_PASS` or prompt). First run creates the vault: prompts for email/password/org slugs and verifies the login before encrypting.
- `groups.sh` / `manage_groups.py` — group manager for every known org/project: `list` (default, status table with age/uptime, instance counts, gateway URLs, SSH lines for running groups), `refresh` (live re-render, Ctrl-C), `start` (bills), `stop`, `wait` (poll one group until running/ready), `delete` (typed-name confirm; leaves a name tombstone). Actions pick a group from a numbered table by # or name.
- `docker/` — image builds (`Dockerfile.multistage` + baked `Dockerfile.lmss_q6_mtp_vision` + model-agnostic `Dockerfile.lmss_generic`), local compose (27B + 9B services), `tests/` — local run/test helpers (`run_27b.sh`/`run_9b*.sh`, `curl1.sh`/`curl2.sh`, `run-nvidia-smi.sh`), plus `check_status.sh` / `version.sh` / `stats.sh` (in-container stats via `/metrics`). See `docker/README.md`.
- `claude/` — the Claude Code ↔ Salad gateway stack: `cl_salad` / `cl_salad_deploy` + `salad_proxy.py` (Anthropic↔OpenAI bridge), gateway test helpers (`curl_salad.sh`, `chat_salad.sh`), and the gateway `salad_api.txt`. See `claude/README.md`.
